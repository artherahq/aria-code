# 仓库地图 (Repo Map)

> 让「第一步」不再是猜一个字符串然后 grep。

## 问题

在这个模块之前，Aria 在陌生仓库里找东西只有一条路：猜一个名字，grep 它。
20 个文件的项目里这没问题；几十万行的企业仓库里它会塌 —— 模型花四五轮去试根本不存在的名字，
而**小模型永远缓不过来**，因为它对「这个代码库把东西叫什么」没有任何先验。
而本地小模型恰恰是这个项目的立身之本。

文件树解决不了这件事：它说的是文件在哪，不是文件里有什么。模型在第一轮真正需要的是
**符号地图** —— 这个仓库定义了哪些类和函数、各自在哪个文件、以及**其中哪些是仓库其余部分真正依赖的**。

## 排序才是全部差别

任何真实仓库的符号数量都远超上下文窗口，所以一份不排序的清单只是换了个形状的 grep。

本模块按「**代码库其余部分伸手进来的程度**」给文件打分：这个文件定义的每个符号，
有多少个*其他*文件提到它。被广泛引用的模块分高；没人 import 的叶子脚本接近零。
这个顺序就是有限预算下地图有用的原因 —— 前 8 KB 描述的正是一次改动最可能碰到的那部分系统。

三条修正让这个数字不说谎，每条对应一种被观察到的失真：

| 修正 | 针对 |
|------|------|
| 少于 4 个字符的名字不计分 | `id` / `get` / `run` / `fn` 和日常词汇碰撞，会把碰巧定义了它们的文件顶到第一 |
| 在超过 5 个文件里定义的名字不计分 | 三十处都有的 `main` / `setup` / `status`，说不出这三十处里哪个重要 |
| 单个符号的贡献封顶 | 一个流行的小工具函数不该压过一个被广泛依赖的文件 |

同一套修正也用在**文件内部**的符号取舍上，另加两条：顶层定义排在方法前面
（类名才是调用方导航用的把手，列它的三个方法信息量远不如列这个类），
私有名排在公有名后面。

> 反例值得记下来：最初的实现按行号取每个文件的前 24 个符号，
> 结果地图开头是 `_TA_SESSION_CACHE`、`_PATHS` 这类私有常量 ——
> 大模块的顶部通常是私有常量和局部 helper，预算全花在了外部调用方永远不会问的符号上。

预算还会在文件之间摊开（`_TARGET_FILES`）：覆盖三十个文件的浅地图是可导航的；
把预算全花在一个文件上的地图，只是一个更差的 `read_file`。

## 不引入新依赖

Python 用标准库 `ast` 精确解析（含嵌套）。其余语言用声明式正则匹配，覆盖
TypeScript / JavaScript / Go / Rust / Java / Kotlin / Swift / Ruby / PHP / C# / C / C++ /
Scala / Shell / SQL / Lua / Dart / Elixir。

这确实不如 tree-sitter 精确，而这个取舍是划算的：**一份到处都装得上的近似地图，
胜过一份卡在原生编译后面的精确地图** —— 地图的职责是把模型指到对的文件，
到了之后确立事实的是 `read_file`。

## 两个工具

| 工具 | 用途 |
|------|------|
| `repo_map(path?, budget_chars?, focus?)` | 排序后的符号地图。陌生仓库第一个调用。`focus` 把调用方已知相关的路径（比如当前 diff 里的文件）提到最前 |
| `find_symbol(name, path?)` | 一个名字定义在哪、被谁引用。**名字不存在时返回近似匹配** —— 半记不清的名字是常态，猜错的代价从四轮降到一轮 |

系统提示里的工作流相应改成 `orient → read → proposal/write → verification`，
并明确：要找一个定义就用 `find_symbol`，别用 `search_code` 去猎。

## 性能

增量重建：按 mtime + size 判断，没动过的文件直接复用已解析的符号。
一次完整扫描（aria-code 自身，682 个文件 / 6700+ 符号）约 1 秒；
回合之间的刷新只是每个文件一次 stat —— 地图只有在「刷新它比它替掉的那轮 grep 更便宜」时才成立。

跳过的目录见 `SKIP_DIRS`：一个没剪掉的 `.venv` 或 `node_modules` 的体量就超过整个仓库，
会同时主导扫描时间和排序结果。

## 和验收闸门的关系

这两步是有先后的。地图指错了地方没关系 —— [验收闸门](acceptance-gate.md)会红。
反过来，如果先做地图而没有闸门，一次被地图带偏的改动没有任何东西会拦住它。
